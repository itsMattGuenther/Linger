## How it ended

*Milestone check: type a word, get the messages that contain it, click one, land
on it in the room it was said in.* Three tasks: the index (2026-08-30), the
endpoint (2026-08-30), and the surface (2026-08-31).

**The spec section is written** — SPEC §4.12, and the search entry in PROTOCOL
§6, both landed with T-1201. The two questions in it were Matt's and were
answered on 2026-08-30:

- **Search is a destination in the left rail, under the rooms, next to
  `media`**, opening in place of the message stream. `Ctrl`/`Cmd`+`K` is a
  shortcut *into* that destination, never a second surface with its own
  behavior.
- **It covers what people typed and the names of the files they shared.** Link
  titles are deliberately out: a title is a cache the server refreshes on its
  own schedule, so indexing one means results changing under people with nobody
  having edited anything.

- ✅ **T-1201 · The index** — effort: **high** — Matt, 2026-08-30
  `message_fts` in `migrations/0004_search.sql`: an FTS5 table with two columns,
  `body` and `filenames`, keyed by the message's implicit rowid. Five triggers
  keep it — three on `messages`, two on `attachments` — and every one of them is
  "throw the row away and write what is true now" rather than an incremental
  edit, so the index cannot drift from the table it indexes. **Nothing in Rust
  writes to it.** The backfill is one `INSERT ... SELECT` in the same migration.

  **No new dependency and nothing for a host to install.** FTS5 ships inside the
  SQLite that sqlx already bundles (`libsqlite3-sys` compiles it with
  `-DSQLITE_ENABLE_FTS5`).

  Four things worth knowing before touching this:

  - **The index carries its own copy of the text.** An external-content table
    (`content='messages'`) would save a few megabytes and cannot produce a
    `snippet()`, which is the whole result list — and a filename does not live
    in `messages` at all.
  - **A deleted message has no row here, not an empty one.** A tombstone empties
    `body` but keeps its attachments, so indexing "the message minus its words"
    would leave it findable by the name of the file it was carrying. The trigger
    deletes the row outright and there is a test for exactly that.
  - **Filenames are joined with `char(31)`**, not a space, because a filename may
    contain spaces and a hit has to be able to say *which* file it matched.
    `validate::filename` strips control characters, so U+001F cannot occur inside
    one.
  - **The tokenizer is `porter unicode61 remove_diacritics 2`.** Stemming is why
    `photo` finds `photos`. Query and index are stemmed the same way, so they
    cannot disagree.

  **Two surprises.** First, **there is no such thing as a 5,000-word message** —
  PROTOCOL §4 caps a body at 8,000 characters, which is nearer 1,300 words. The
  acceptance test posts the largest message the API will take, nine of them, and
  asserts the insert path has not become something you can feel; it is a guard
  against a quadratic regression, not a benchmark. Second, the backfill can only
  be tested by *removing* the index: the test posts real messages, drops the
  table and its five triggers (which puts the server exactly where an old one
  is), then replays the shipped migration file over it with `include_str!`.

- ✅ **T-1202 · The endpoint** — effort: **medium** — Matt, 2026-08-30
  `GET /search?q=&room_id=&author_id=&before=&limit=` in
  `routes/search.rs`, over `repo::search`. `crates/linger-server/tests/search.rs`
  covers all three acceptance cases and ten more.

  **The query is rebuilt, never forwarded.** FTS5 has a query language of its
  own, and handing it somebody's raw typing means either a syntax error thrown
  at whoever typed an apostrophe, or a search that quietly did something other
  than what it looked like. `Terms::parse` takes the searchable runs out of the
  string and wraps each in quotes, and quoting is what makes every operator
  inert — `AND`, `OR`, `NEAR`, `*`, `(`, `^` all arrive as words to look for.
  There is no input that reaches `MATCH` as syntax, and a test fires eight of
  them at it. **Do not "simplify" this by passing `q` through.**

  **A snippet arrives as runs, not as a marked-up string.** `SearchHit.snippet`
  is a `SearchSnippetPart[]` of `{ text, matched }`, because any marker
  character is a character a message could contain — and because the obvious
  rendering of a marked-up string is to drop it into HTML. Nothing to parse,
  nothing to escape.

  **Paging is keyset on the message id** and the cursor is that id, hex. UUIDv7
  bytes sort chronologically, so `before` is a range scan and the order is the
  same one the stream reads in. There is no relevance ranking and SPEC §4.12
  says there will not be one.

  Two things that caught the tests out, both about limits rather than search.
  A validation refusal here is **422**, not 400 (`ApiError::validation`). And
  `RATE_SEARCH` (30/min) refills while a burst of requests is in flight, so the
  test asserts the refusal lands *after* the burst is spent rather than on an
  exact request number — the same shape any future rate-limit test wants.

- ✅ **T-1203 · The search surface** — effort: **medium** — Matt, 2026-08-31
  `client/src/search/` — `SearchPanel.tsx`, the pure copy and label helpers in
  `search.ts`, and `search.css`. A destination in the rail under the rooms,
  next to `media` (SPEC §3), taking the stream column the way the media
  collection does. `Ctrl`/`Cmd`+`K` opens the same panel with the box focused
  and re-focuses it when it is already open — a way *in*, never a second
  surface. Search-as-you-type after a 320 ms pause, filters for room and
  person, keyset paging on the hit's cursor, and a hit drawn as one line: who,
  where, when, and the snippet with the matched runs in `<mark>` (weight and
  full-strength text, not a highlighter — a colored block behind text is the
  one thing that would make this screen look like somebody else's app).

  **Two things moved that the task did not name, and both were the docs being
  right about code that was not.** `media` sat *above* the room list with a
  comment explaining why; SPEC §3 draws both destinations *under* it, and the
  docs win, so `media` and `search` are now one section below the rooms behind
  a full-bleed hairline. And an open destination now takes the same accent rule
  an open room does (`aria-pressed`), which `media` had been quietly missing.

  ### The scroll was the hard part, and not for the reason the task said

  The task expected T-303's re-aiming problem, and that is real, but it was the
  second problem. The first one is that **the client could not reach the
  message at all.** `loadUntil` pages backwards ten pages — a thousand messages
  — and the acceptance criterion's hit is 8,200 messages behind the newest.
  Eighty-two sequential round trips is not a fix.

  So `GET /rooms/:id/messages` grew **`around=<id>`** (PROTOCOL §4): the message
  plus as much either side of it as `limit` allows, in one request. It is
  additive and no existing client notices. Two details are load-bearing:

  - **The halves are capped separately and neither borrows from the other.**
    A window near an edge comes back short rather than growing the other side,
    which is what lets a client read each half on its own — a short older half
    is the start of the room, a short newer half is the newest message. A
    window that quietly filled itself would make both signals a guess.
  - **`after` on that endpoint could not be used to read forwards.** It answers
    newest-first, so it hands back the *newest* hundred messages after a point
    rather than the next hundred — which is precisely the gap. Reading forwards
    out of a window is another `around`, centred on the newest message held, so
    the two pages overlap by construction. It costs half a page of messages
    already held, and that is the price of never producing a gap.

  ### A room can now be behind its own newest message

  `RoomStream` grew **`atEnd`**, and it is the part to be careful with. A room
  opened on a search hit is *detached*: live `message.create` frames for it are
  **dropped** rather than folded in, because a message from today merged into a
  February window sits next to one from eight months earlier with nothing
  between them and nothing to say so. An invisible gap is worse than a message
  that shows up when you scroll back down to where it belongs. An *update* to a
  message the window already holds still lands — that changes something that is
  there rather than adding something that is not.

  Everything that assumed "the bottom of this list is the newest thing said
  here" had to learn to check: the read marker (a detached window must not mark
  the room read), the walk-in scroll, follow-on-append, and the composer —
  saying something out of a window puts you back at the newest, because the
  alternative is a message you just sent that appears nowhere. `back to the
  newest` in the room header is the shortcut; reading forwards to the end gets
  there too.

  ### Two real bugs, both invisible in a test

  Both were found by running it, and neither would have failed a unit test.

  **The jump held a stale row index.** It cached the target's index and re-aimed
  at that number for up to 90 frames. Meanwhile the jump passed through the top
  of the list, which fired `loadOlder`, which prepended a page and moved every
  index below it — so the next frame aimed a hundred messages earlier, which
  fired another page. It walked all the way to the first message in the room,
  intermittently, and looked like "the scroll landed in the wrong place". The
  fix is two lines: look the row up by id **every frame**, and hold backfill off
  while a jump is in flight.

  **The jump settled on a list of guesses.** Stopping when the aim had held
  still for a few frames looked right and was wrong: at the moment a jump
  starts, every row is the same estimated height, so the aim is perfectly
  stable and perfectly wrong, and it stays that way until the first
  measurements arrive from a ResizeObserver — which reports after a paint, not
  on the frame clock. It settled in five frames and the real heights then
  pushed the message off the top. Done is now: the row is **on screen** (not
  merely drawn — the virtualizer keeps a margin of rows either side of the
  viewport), and **both the aim and the measured total height** have held still
  for five frames, after a floor of twenty frames.

  ### How it was checked

  A throwaway server with 10,000 messages seeded straight into SQLite across
  eight months, one of them carrying the word `carburettor` at message 1,801 —
  6.5 months back — and one carrying `drive-cage-invoice.pdf`. The desktop
  client driven with a uinput keyboard and pointer under KWin. Searching the
  word returns the one hit; clicking it opens the room with that message on
  screen, centred, with history either side; the filename hit says
  `file: drive-cage-invoice.pdf` because the message text ("here it is") does
  not carry the match. Four consecutive cold runs — back to the newest, search,
  click — landed identically. `back to the newest` returns to today, and
  scrolling down out of a window pages forward with nothing skipped.

  **Two things the seeding taught.** The attachment triggers in
  `0004_search.sql` are `AFTER UPDATE`, not `AFTER INSERT`, because the real
  flow reserves an upload and *attaches* it when the message is posted — a row
  inserted already attached is not indexed, and a seeding script has to do it
  the way the app does. And deleting `linger.db-shm` out from under a running
  server leaves it reading a stale snapshot with no error at all: the API
  answered `[]` for messages that were plainly in the file. Restarting fixed
  it; do not touch the WAL sidecar files of a live server.

  **What is not proven.** One machine, one client, one person. Nobody has run a
  search while somebody else was posting into the room being read, which is the
  case `atEnd` exists for — the unit tests cover it, a second computer has not.

  **2026-10-22, #698 (the client's side of older history).** The store still
  loads and lets go of history as above (`loadOlder`, `trimHistory`); what
  changed is when the conversation shows it. On an iPhone a page of older
  history that arrives while the conversation moves waits out of sight until
  it's still, and no further page is asked for meanwhile: WebKit stops a
  glide the page moves the scroll position in, so the virtualizer held back
  the correction that keeps a page arriving above from moving the reader, and
  the view was thrown a page further with each one. On every engine, rows above
  the screen are measured while it's still, and the landing and a hand on the
  conversation end the virtualizer's own aim at a row, which otherwise pulled
  the view to that row when a page went in above. `docs/design/architecture.md`,
  "A glide in a conversation", has the mechanics.
